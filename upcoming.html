CURATOR Planning Record

Planned Changes for Next Release

Updated On: October 4, 2026 at 2:06 PM EDT

What We're Working On

Upcoming improvements for myOrganizer: CURATOR v2.5.xx, following v2.0.0-beta.6.

These are the improvements currently planned for the next CURATOR release. Development is still underway, so the final list may change before release.

CURATOR v2.0.0-beta.6 remains the current public release. Read its release changelog for the changes already available.

Adding

  • Append inventories existing output files and directories during file discovery. Collision routing and unchanged-output decisions are planned in the database; Clear skips the output scan.

Changing

  • Platform registration, DAT selection and scan preparation reuse database evidence and perform metadata selection, grouping and publication through Core database operations, reducing repeated processing.
  • Collection publication obtains output counts and collection contracts from the database while retaining the existing Core output and recovery operations.
  • Reporting uses database projections for authority, coverage, audit metadata, reconciliation selection and report summaries, reusing its physical inventory across those operations.
  • The dedicated json folder and its obsolete archive/clear action and history settings have been retired. Configuration, retained DAT references, runtime status, manifests and reporting JSON continue in their supported locations.
  • Gateway stage and utility dispatch, DAT selection, mapping templates and reporting destinations use their configured paths and references throughout the pipeline.
  • Supported logging, recovery-admission and final workspace-cleanup settings are honored consistently. Obsolete settings for retired or inactive operations have been removed.
  • The machine-readable Reporting.json summary is published in the configured reporting folder alongside the other reports.
  • CHD scan preparation extracts directly into the workspace, avoiding a second copy of decoded tracks while preserving extraction-time track identities and descriptor hashing.
  • Stages 1–3 reuse retained authority when their consumed sources and relevant policy are unchanged across runs; a new RunID alone does not require rebuilding.
  • Single-file and multi-file ZIP output use bounded native 7-Zip batches with Normal compression and a default ceiling of 24 archive workers. Each ZIP group shows one completed-file count bar, counting only outputs that need creation.
  • Ordinary output failures are recorded while remaining outputs continue. Resume retries unfinished outputs and retains successful ZIPs; catastrophic failures can still stop processing.
  • Collection preparation and validation use relational stage results without building obsolete intermediate JSON summaries.
  • Stage 9 reuses database evidence and performs collection classification, routing, artifact planning and incomplete-set consolidation through retained relational data, reducing repeated processing while preserving output plans and source memberships.
  • Stage 10 keeps workspace contents until output creation and collection catalogue publication finish, then, when Execution.Workspace.CleanOnFinish is enabled, deletes the contents in one final pass while preserving the workspace folder.
  • Application screens, current README references and newly generated reports use the myOrganizer: CURATOR v2.5.xx identity.

Fixing

  • Gateway clears and maximizes the console before displaying the startup README, restoring its established behavior.
  • The modified-chdman README notice uses separated paragraphs for readability, preserving its wording.
  • Gateway preserves a durable failure outcome when Core startup rejects configuration.
  • Stage 1 follows configured platform-file patterns and subfolder selection, applies complete DAT filename patterns consistently, using the shared configured source folders. MAME listxml selection is configured through DAT.Source.MameFilePattern; an empty value disables that additional selection.
  • The Core API handbook documents native ZIP batch member contracts, compression parameters and current single-file ZIP dependencies and compatibility parameters.
  • The Admin, End User and Quick Start guides explain retained authority reuse, native ZIP compression and count progress, ordinary output-failure continuation and Resume, and the limits of unchanged Append detection.
  • The stage-completion prompt keeps the input cursor on the same line as the prompt.
  • Stage 9 correctly builds retained MAME references during collection planning.
  • Append completes known unchanged outputs from discovery and retained database receipts without repeating file checks, content hashes or archive inspection in Stage 10, including unchanged incomplete sets. Keep the output folder unchanged during the run; this path does not detect same-size external content changes.
  • On a clean installation without a collection database, the Gateway shows only P — Prepare DAR and rejects other menu selections until the database exists. The Admin, End User and Quick Start guides explain first-run preparation, retrying failed preparation, and when to organize a collection.
  • Gateway API handbook generation completes with the supported general Core catalogue, excluding application-internal database commands. Catalogue, index and parameter tables now keep their headings together in one repeated header row.
  • Stage 10 can resume after catalogue publication or final workspace cleanup fails, completing the remaining work without creating a duplicate collection generation.
  • Final workspace cleanup reports deletion failures and marks progress complete only after deletion finishes. Read-only contents can cause ordinary deletion failures.
  • Existing v2.0.0-beta.6 databases at schema 26 remain compatible with v2.5.xx, preserving their original creation identity.
  • Reporting regenerates cached reports when the application version changes, preventing reuse of reports carrying an older application version.
  • The Admin, End User and Quick Start guides now describe the current application identity, schema-26 database compatibility, and Stage 10 publication and final-cleanup recovery.
  • The operator guides remove the retired root-JSON maintenance option and folder, and identify the configured Reporting destination. The refreshed Core API handbook describes relational recovery dependencies and current exported APIs.
