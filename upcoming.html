CURATOR Planning Announcement

Planned Changes for Next Release

What We're Working On

CURATOR is now on the v2.xx.xx development track. This is the sole current application-version track, but no public v2.xx.xx release has been packaged or published. The candidate changes below remain possible future work and may change before release.

Adding

  • Adding capability-based Bootstrap initialization through strict, validated static JSON call sheets for Gateway, numbered stages, and utilities.
  • Adding the relational Core.Database runtime and coordinated persistent and disposable stage-state contracts.
  • Adding the pinned Microsoft.Data.Sqlite, SQLitePCLRaw, and native e_sqlite3 runtime dependencies required by Core.Database.
  • Adding limited, preliminary ingestion of content-validated MAME -listxml exports for coin-operated Arcade ROM and CHD authority without relying on an mame*.xml filename.

Changing

  • Changing Gateway base startup so it requires no database capability and activates additional capabilities only for the selected action.
  • Changing Gateway startup ordering so the safety agreement precedes requested Core activation.
  • Changing Gateway prerequisite handling so Stages 2-10 and Reporting display an end-user notice and close normally when Stage 1 has not initialized the database authority.
  • Changing Stages 1-10 to use the promoted relational authority and frozen execution-plan pathway proven by the successful Test_Bed Full Run.
  • Changing Stage 10 execution to retain one Core-owned SQLite connection, atomically pipeline the next InFlight checkpoint with each completed receipt, and use WAL with synchronous=FULL for faster durable publication.
  • Changing Stage 3 subsequent runs to retain the active DAR revision without rebuilding or republishing authority when Stage 1 and Stage 2 inputs are unchanged.
  • Changing Stage 2 and Stage 3 relational publication to reuse prepared SQLite commands within their existing atomic transactions.
  • Changing the sole current application identifier to CURATOR and the current development version to v2.xx.xx across source, configuration, templates, memory, inventory, and user documentation.
  • Changing current Core and stage component provenance from historical v.5-dev_### and v.5-New_### forms to concise DEV_### labels while retaining old identifiers only as explicitly historical evidence.
  • Refreshing current guides to the CURATOR v2.xx.xx identity with verified pre-change backups, actual-update-date filenames, relational-runtime guidance, and complete rendered-page inspection.
  • Documenting the 149-interface general Core API registry while identifying Core.Database's separate application-internal relational contract.
  • Changing Stage 3 authority-set identity to include the canonical DAT key and publishing that key through DAR provenance so physical DAT filenames do not define or collapse authoritative set identity.
  • Changing MAME Arcade output to split-set structure with machine-owned ROM membership and separate parent, BIOS, and device dependency sets.
  • Prioritizing MAME internal CHD SHA-1 authority over Redump-derived optical-track evidence on the MAME path.
  • Changing complete authoritative-set publication so applicable optical transformation requires one CUE while complete sets without usable CUE evidence publish as ZIP sets.
  • Preserving distinct Redump and TOSEC authority sets when identical content appears in both sources.
  • Selecting Redump cue authority by authoritative DAT SHA-256 and pinning each configured cue archive by SHA-256.
  • Refreshing the bundled Redump cue and GDI metadata archives and expanding configured platform coverage.

Fixing

  • Fixing relational Matching input reconstruction so persisted CUE references, CUE scope, and complete members of positively identified authority sets remain available for deterministic optical-set correction.
  • Fixing safety-notice presentation so the locked canonical README content is rendered as readable console text without changing its source.
  • Fixing resolved candidate destination collisions remaining as blocking readiness failures after final artifact routing produces distinct destinations.
  • Retaining existing authority memberships when optical-container refinement adds deterministic set-scoped evidence.
  • Collapsing exact duplicate records within one authority membership before DAR publication while preserving distinct Redump and TOSEC memberships.

Continuing Limitations

  • Continuing to treat MAME support as limited and preliminary: excluding nodump, routing incomplete authority sets to NeedsAttention, and not providing merged, non-merged, standalone, software-list, or general non-Arcade MAME management.
